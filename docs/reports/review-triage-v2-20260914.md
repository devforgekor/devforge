## 0. 요약

- V1·V2 모두 **v1의 실측 교정(32툴, 0회 리스트, 12↔16, 448줄, 7152건)을 수용**.
- **핵심 충돌은 R4(MCP 순서)**: v1은 "M2→M1→M3(훅 먼저)"로 기각, V2는 "M3→M1/M2(merge 먼저)"로 번복 요구.
- **재분석 결론: 둘 다 부분적으로 옳다 → "계약 동결(contract-first)"이 선행.** R4는 **부분수용**으로 번복.
- **R3(Phase H)도 부분수용으로 번복**: H0(빌드 파이프라인)는 병행, 실제 단일 이미지 교체는 A~G 후.
- **R7 → 부분수용** (V1·V2 합의), **A5 → 조건부 수용** (원본 로그 유무에 따라 분기).
- V1·V2가 제기한 신규 리스크(SPOF/RTO·RPO, 비용 하드캡, 데이터 보존, SBOM)를 수용.
- **검증자 오류 1건**: V1은 "12 = 서버 계약(서버가 노출할 툴 수)"이라 했으나, 서버 노출은 **25**이고 12는 **클라이언트(devforge) 로드 수**다. V2의 해석이 정확.

## 1. 검증 응답 요약

### 1.1 V1 (트리아지 타당 + R7 재분류)
- 종합: 실측 기반 판정 대체로 타당. F9(auto_log 운영)가 deepseek의 greenfield 프레이밍을 무효화한 결정적 실측.
- **R3 기각 타당**(단, 점진적 이미지 빌드는 허용). **R4 기각 타당**. **R7 → 부분수용 재분류**.
- A6 불가피(계약 축소 대안 불성립: 클라이언트 무변경 기준 위배).
- 정정치(32, ≈15) 옳음. 단 "12"는 별도 정당성.
- A5: 원본 로그 없으면 `legacy_unknown` 명시 + 수락기준 재정의.
- Q6: **Observability를 Phase 0에**, D1 비용분석 Phase C 전, 롤백 매트릭스를 MCP 순서 앞으로.
- Q7: SPOF, D1 비용, 데이터 보존/규정, ARM 리소스 정량 부재.

### 1.2 V2 (R3·R4 번복 요구)
- 종합: 조건부 승인. **API 하위호환 패턴 간과(R4)**, **단일 서버 배포 오버헤드 과소평가(R3)** 수정 조건.
- **R4 [미수용→부분수용]**: 서버 merge+alias(M3) → 클라이언트 훅 마이그레이션(M1/M2) → 구툴 제거(M0) 순서가 표준.
- **R3 [미수용→조건부수용]**: 단일 이미지 **빌드 파이프라인**은 조기 구축, A~G 코드는 로컬 마운트/오버레이 테스트.
- R7: 양안 비교 판정 합리적.
- A5: `legacy:pre-sept-2026` 명시 마커.
- Q6: MCP 내부 순서 명시(M3→M1/M2→M0) + Observability/Rollback Drill 게이트.
- Q7: SPOF+RTO/RPO, 비용 하드캡, **SBOM/공급망**.

## 2. 충돌 해소: R4(MCP 순서) — v1 기각 → **부분수용(계약 동결 선행)**

### 2.1 쟁점
| 입장 | 주장 | 근거 |
|---|---|---|
| v1·deepseek·V1 | 훅(M2→M1)이 merge(M3)보다 먼저 | 최고가치(수집 커버리지) 지연 방지, 표면 2회 churn 회피 |
| qwen1·V2 | merge(M3)가 훅보다 먼저 | 표준 API 마이그레이션(서버 변경+alias → 클라이언트 이전 → 구툴 제거), 클라이언트 워크플로우 파손 방지 |

### 2.2 시스템 사실에 근거한 분해
- **M1(deepdive lifecycle)과 M3(memory/search/schema/plan)는 툴 집합이 분리** → 서로 독립. 순서 강제 없음.
- **M2(obs 자동캡처)와 M3(obs_write/obs_search → memory(action,kind))는 실질 의존**. M2 훅이 `obs_write`에 쓰도록 먼저 만들면, M3 merge 후 **재작업**이 발생한다.
- 즉 V2의 우려는 **M2↔M3 구간에서만 타당**하고, M1에는 해당하지 않는다.

### 2.3 해소안 (contract-first)
1. **M3의 목표 툴 계약(이름·스키마) + 구툴 alias를 먼저 동결**한다(구현 전체가 아니라 계약).
2. **M1·M2 훅을 동결된 계약 대상으로 구현**한다(obs 캡처는 `memory(action=save,kind=obs)` 대상).
3. **M3 구현을 완료**한다(서버 파사드).
4. **M0에서 구툴을 제거**하고 M4(annotation·pinning)로 마감한다.

> 결과: "M3 전체 선행"(V2)도 "M1/M2 전체 선행"(v1)도 아니다. **계약 동결이 선행**. v1의 가치 지연 우려와 V2의 호환성 우려를 동시에 충족.

**R4 판정: 부분수용(번복).** V2의 방향을 수용하되 "M3 전체 선행"은 과잉으로 기각.

## 3. 충돌 해소: R3(Phase H) — v1 기각 → **부분수용**

- v1 우려(타당): 0줄 stub(F4)을 이미지에 구우면 비파괴 원칙 위배.
- V2 우려(타당): 4코어 ARM에서 Phase마다 독립 이미지 빌드는 리소스 낭비.
- **해소:** Phase H를 둘로 분리.
  - **H0(병행):** 단일 이미지 **빌드 파이프라인 + 테스트 환경**을 A~G와 병행 구축. A~G 코드는 로컬 마운트/오버레이로 테스트 → stub baking 회피.
  - **H(후행):** A~G 완료 후 실제 프로덕션 단일 이미지 교체 + digest 고정.

**R3 판정: 부분수용(번복).** "H가 A~G보다 먼저"라는 원 주장은 여전히 기각.

## 7. 통합 권고 (v2 우선순위)

5. **수치 정합:** 32툴 / 0회 9개 정정 / 목표 ≈15 / merge −8 / day_cycle 448 / turns 7152 / 12↔16 분리.
6. **D1 비용·거버넌스 분석** (Phase C 전).
7. **리스크 보강:** ARM cgroups/nice/OOM, 훅 API 파손→폴링 폴백, pgvector 재색인, SPOF/RTO·RPO, 예산 하드캡, SBOM(선택).
